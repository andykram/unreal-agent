The `examples/` directory contains larger workflows and a structured-output example. Each script uses
Python to build one static graph, then calls `flow.export()`.

Open a source viewer below and select an annotation to jump to its highlighted
lines. Source is imported from the runnable examples when the site builds.

:::caution[Descriptions, not operations]
Commands, deployments, database changes, agents, and worktrees are simulated.
The command paths in these examples describe intended operations. They do not
require those programs to exist. Worktrunk names and bases remain metadata.
Prompts describe evidence handling; the prototype does not transfer artifacts.
:::

## Run an example

From `cmd/workflow-prototype`, start the viewer:

```sh
./run.sh -script examples/service_release.py
./run.sh -script examples/migration_rehearsal.py
./run.sh -script examples/investigation.py
```

Add `-json` to inspect the validated graph without simulation. Add `-auto` to
pass ready checks automatically until approvals prevent further progress.

In the viewer, `n` advances ready work. Use `p ID` or `b ID` for check results,
`a` to approve all ready approvals, and `f ID` to inject an execution error.
Reset with `r` before exploring another outcome. See the
[viewer reference](/reference/cli/) for all controls.

## Four-service release

**Source:** `examples/service_release.py`.

Four service routes share a contract baseline, then use independent workspaces.
Each route has parallel lint and compatibility checks, bounded repairs, review,
approval, rollout observation, and a possible rollback.

| Scenario | What to simulate | Expected route |
| --- | --- | --- |
| Healthy release | Pass `api-verify`, approve, then pass `api-observe` | `api-healthy` reaches `api-settled` |
| Rejected implementation | Exhaust all three `api-verify` checks | `api-rejected` completes; rollout skips |
| Rollback | Pass verification, approve, then exhaust both observation checks | `api-rollback` reaches the service join |
| Operational failure | Inject an execution error in a required step | That service join and the final report remain blocked |

Repeat with `worker`, `billing`, or `gateway` prefixes. The final report waits
for all four service joins. A rejected service can be reported without implying
that it shipped. The archive approval is a separate final gate.

## Staged migration rehearsal

**Source:** `examples/migration_rehearsal.py`.

The graph progresses through expand, backfill, and contract stages in one
workspace. Each stage rehearses changes, checks a canary, and requests approval
before widening. Only its accepted path starts the next stage.

| Scenario | What to simulate | Expected route |
| --- | --- | --- |
| Full rehearsal | Approve the initial gate, then pass checks and approve each stage | All stages advance, followed by audit |
| Preflight rejection | Exhaust `expand-rehearse` | Expand records a stop; later stages skip; audit remains reachable |
| Canary rollback | Pass rehearsal, then exhaust `backfill-canary` | Rollback and verification run; contract skips; audit remains reachable |

Each stage joins its accepted, rejected, and rolled-back endpoints. The final
join tolerates skipped later stages, so an early stop still receives an audit.
An execution error blocks the affected route instead of becoming a normal rejection.

## Multi-strategy investigation

**Source:** `examples/investigation.py`.

Trace, database, and runtime investigations use separate workspaces. Each primary
probe can enter deeper validation or a fallback investigation. Validation and
fallback checks each split again before joining a strategy summary.

| Scenario | What to simulate | Expected route |
| --- | --- | --- |
| Supported hypothesis | Pass `traces-probe` and `traces-validate` | Supported route reaches the summary |
| Counterevidence | Pass `database-probe`, exhaust `database-validate` | Disputed route reaches the summary |
| Recovered evidence | Exhaust `runtime-probe`, pass `runtime-fallback-check` | Fallback findings reach the summary |
| Inconclusive strategy | Exhaust a primary probe and its fallback check | Unresolved route still reaches synthesis |

Synthesis waits for all three summaries. A final challenge check leads to either
publication approval or an evidence-gap report. Both converge on a handoff.
No semantic evaluator verifies the investigation's conclusions.

## Agent map, reduce, and chain

**Source:** `examples/agent_pipeline.py`.

Three research agents produce evidence in separate workspaces. A reducer receives
their actual output objects. A critic and editor then run in sequence, with the
original brief preserved as shared context. The publication's `approved` field
selects publish or follow-up work.

```sh
./run.sh -script examples/agent_pipeline.py
```

Enter `n` twice to create workspaces and start the three research agents. Supply
results with `o research-0 JSON`, `o research-1 JSON`, and `o research-2 JSON`.
Each result needs `topic`, `sources`, `finding`, and `confidence` between 0 and 1.
Advance with `n`, supply a `Brief` to `brief`, then advance and supply each chain
result to `publication-critique` and `publication-edit`. The viewer displays the
resolved inputs passed to each agent.

## Four-service delivery pipeline

**Source:** `examples/delivery_pipeline.py`.

This 28-node graph combines typed outputs with parallel planning, serial
implementation/review chains, mapped verification, and a readiness reducer.
Each chain preserves its charter and plan in shared context.

```sh
./run.sh -script examples/delivery_pipeline.py
./run.sh -script examples/delivery_pipeline.py < examples/delivery_pipeline.inputs.txt
```

The input tape supplies coherent successful results. Change the `assess-readiness`
result to `ready: false` to explore escalation. Its decision comes from submitted
agent output; the harness does not independently compute that every service passed.

## Read the convergence boundaries

An ordinary dependency requires completion. Any skipped input skips an ordinary
node. A `join` instead waits for all inputs to complete or skip, with at least
one completed input. All-skipped inputs skip the join; execution errors block it.

These examples join **route endpoints**, not raw check outcomes. An exhausted
check has status `completed` with outcome `failed`. Joining that check directly
would not establish permission to release, migrate, or publish.

See the [Python API](/reference/python-api/#join) and
[execution model](/explanation/execution-model/#skipping-and-joins) for exact semantics.
